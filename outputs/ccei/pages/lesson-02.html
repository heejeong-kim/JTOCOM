실습

서비스 뜯어보며 이해하기

2.1 한 번에 뜯어보기

두 프롬프트 중 하나를 골라 씀. ①은 화면·흐름 정리, ②는 웹앱 기초까지 연결한 분석.

① 핵심 서비스 분석 프롬프트

나는 코딩과 서비스 기획 용어를 하나도 모르는 완전 초보자야.
첨부한 화면 캡처를 보고{URL 넣어도 됨}, 이 서비스를 아래 순서대로 뜯어봐 줘.
각 항목마다 서비스 만드는 사람들은 이걸 뭐라고 부르는지 이름을 알려주고, 쉬운 말로 설명해줘.

1. 화면이 어떤 부분들로 나뉘어 있는지 위에서부터 차례로 알려줘.
   표(이름 | 화면의 어디 | 하는 일)로 정리해줘.
2. 맨 위 메뉴를 보고, 어떤 메뉴가 있고 각 메뉴 아래에 어떤 페이지가 들어 있을지 큰 것부터 작은 것 순서로 정리해줘.
3. 사용자가 이 서비스에 들어와서 가장 중요한 일을 끝내기까지 어떤 화면을 어떤 순서로 거치는지 화면 → 화면 형식으로 한 줄로 보여줘.
4. 화면에 보이는 정보(예: 공지, 공고, 목록) 하나에 어떤 항목들이 들어 있을지 표(항목 | 글자·날짜·숫자 | 꼭 있어야 하는지 | 예시)로 정리해줘.
5. 내가 버튼이나 목록 하나를 누르면 눈에 안 보이는 뒤쪽에서 어떤 일이 순서대로 일어나는지 아주 쉽게 설명해줘.

화면만 보고 확실히 알 수 없는 내용은 반드시 '추측'이라고 표시해줘.
마지막에 1~5에서 나온 이름(용어)만 모아서 한 줄 뜻과 함께 정리해줘.
예시 · 펫프렌즈 뜯어보기 결과 ↗

② 웹앱 기초까지 연결한 상세 분석 프롬프트

화면과 이용 흐름을 1교시 웹앱 기초 개념에 연결해 살펴봄.

나는 바이브코딩을 배우는 초보자야. 첨부한 화면 캡처나 URL의 특정 서비스를 기준으로 1교시의 웹앱 기초까지 연결해 자세히 분석하고 싶어.
분석 대상: {서비스명, 화면 캡처 또는 URL}
이 프롬프트만으로 분석할 수 있게 입력한 화면 캡처나 URL을 기준으로 설명해줘. 다른 예시 서비스로 바꾸지 말고, 이 서비스에서 확인되는 화면 구성·메뉴·사용자 흐름·정보 항목에 연결해줘.
화면만으로 알 수 없는 내부 구조나 기술은 사실처럼 단정하지 말고 '추측'이라고 표시해줘.

아래 항목마다 '쉬운 뜻 | 이 서비스에서 해당되는 화면·기능 | 바이브코딩할 때 AI에게 할 요청 예시 | 확인된 사실/추측' 표로 정리해줘.

① 화면(프론트엔드)·서버(백엔드)·데이터(CSV·엑셀·브라우저 저장소·데이터베이스)의 역할과, 이 서비스에서 사용자가 버튼을 눌렀을 때 요청(Request)과 응답(Response)이 오가는 흐름
② HTML·CSS·JavaScript의 역할을 이 서비스의 화면 요소·모양·동작에 연결한 설명
③ CSV·엑셀·브라우저 저장소·데이터베이스(DB), API·OpenAPI·JSON의 뜻과 이 서비스에서 쓰일 수 있는 위치. 실제 사용 여부를 화면만으로 확인할 수 없다면 추측으로 구분
④ 로컬(Local) 실행, 개발자 도구·콘솔, 오류 메시지, 버전·체크포인트, 배포(Deploy), URL·도메인의 뜻을 이 서비스를 만들고 점검하는 과정에 연결한 설명
⑤ API 키·환경 변수(.env), 인증·권한, 개인정보 보호를 이 서비스를 안전하게 만들 때 어떻게 고려할지
⑥ PRD, MVP, 페르소나, 유저 플로우, IA·메뉴 구조도, 와이어프레임, 화면 설계서, 기능 명세서, 데이터 명세서, 완료 조건의 뜻과 이 서비스에서 만들 수 있는 기획 자료 예시
⑦ 헤더, GNB, LNB, 사이드바, 히어로, 푸터, 브레드크럼, 그리드, 앱바, 탭, 내비게이션 바·드로어·레일, 텍스트 필드·텍스트 영역·검색바, 플레이스홀더, 라벨·도움말·오류 메시지, 파일 업로드, 버튼·메뉴, 카드·목록, 알림·모달 중 화면에서 확인되는 용어를 위치와 함께 설명
⑧ 색·글꼴·간격·버튼 모양을 정하는 디자인 시스템과 모션이 이 서비스 화면에 어떻게 적용되어 있는지. 확인할 수 없는 항목은 추측으로 표시

마지막에는 이 서비스의 핵심 기능 하나를 기준으로 '사용자 행동 → 화면 → 서버/데이터 처리 → 결과 표시 → 점검·배포'를 한 줄로 연결해줘. 설명은 초보자가 이해할 수 있게 쓰고, 전문 용어는 처음 나올 때 쉬운 뜻을 바로 붙여줘.
참고용 · 항목별 프롬프트를 하나씩 보고 싶을 때 열기

  1. ① 화면 각 부분의 이름 알기 · UI 용어

    첨부한 화면을 보고, 화면이 어떤 부분들로 나뉘어 있는지 위에서부터 차례로 알려줘.
각 부분을 서비스 만드는 사람들은 뭐라고 부르는지 이름도 알려주고, 나는 그런 이름을 하나도 모른다고 생각하고 쉬운 말로 설명해줘.
표(이름 | 화면의 어디 | 하는 일)로 정리해줘.

  2. ② 메뉴가 어떻게 나뉘었는지 보기 · 메뉴 구조도

    이 화면 맨 위의 메뉴를 보고, 이 사이트에 어떤 메뉴가 있고 각 메뉴 아래에 어떤 페이지가 들어 있을지 큰 것부터 작은 것 순서로 정리해줘.
이렇게 정리한 것을 서비스 만드는 사람들은 뭐라고 부르는지도 알려줘.

  3. ③ 사용자가 거쳐 가는 순서 보기 · 유저 플로우

    사용자가 이 서비스에 들어와서 가장 중요한 일을 끝내기까지, 어떤 화면을 어떤 순서로 거치게 될지 알려줘.
화면 → 화면 형식으로 한 줄로 보여주고, 이런 순서를 정리한 것을 뭐라고 부르는지도 알려줘.

  4. ④ 화면에 담긴 정보 정리하기 · 데이터 명세서

    이 화면에 보이는 목록 항목 하나(예: 상품, 게시글, 공고)에는 어떤 정보들(예: 제목, 날짜, 가격)이 들어 있을지 정리해줘.
각 정보가 글자인지·날짜인지·숫자인지, 꼭 있어야 하는지도 표로 알려줘. 화면에서 안 보이는 건 '추측'이라고 표시해줘.
이런 표를 뭐라고 부르는지도 알려줘.

  5. ⑤ 화면 뒤에서 일어나는 일 알기 · 서비스 구조

    내가 이 서비스에서 버튼이나 목록 하나를 누르면, 눈에 안 보이는 뒤쪽에서는 어떤 일이 순서대로 일어나는지 아주 쉽게 설명해줘.
설명에 꼭 필요한 기본 용어는 내가 하나도 모른다고 생각하고 한 줄씩 뜻을 알려줘.

  6. ⑥ 화면을 만드는 세 가지 보기 · HTML·CSS·JavaScript

    이 화면에서 글자·버튼·입력칸처럼 '무엇이 있는지', 색·크기·배치처럼 '어떻게 보이는지', 누르면 바뀌는 것처럼 '어떻게 움직이는지'를 나눠서 알려줘.
각각을 만드는 HTML·CSS·JavaScript가 무엇인지 나는 하나도 모른다고 생각하고 쉬운 말로 설명해줘.
표(화면 요소 | HTML·CSS·JavaScript 중 무엇 | 하는 일)로 정리해줘.

  7. ⑦ 정보가 어디에 저장되고 연결되는지 보기 · 데이터·API

    이 서비스에 보이는 정보(목록, 내 기록, 장바구니 등)가 어디에 저장되어 있을지 알려줘.
파일(CSV·엑셀), 브라우저 저장소, 데이터베이스(DB) 중 무엇일 것 같은지, 다른 곳에서 정보를 받아온다면(API) 어떤 정보일지도 알려줘.
화면만으로 알 수 없는 건 '추측'이라고 표시하고, 용어마다 쉬운 뜻을 붙여줘.

  8. ⑧ 만들고 고치고 공개하는 과정 보기 · 로컬·오류·배포

    내가 이런 서비스를 직접 만든다면, 내 컴퓨터에서 먼저 실행해 보고, 오류가 나면 고치고, 다른 사람이 쓸 수 있게 인터넷에 공개하기까지 어떤 순서로 진행되는지 알려줘.
로컬, 오류 메시지, 개발자 도구, 버전 저장, 배포, URL·도메인 같은 말이 나오면 쉬운 뜻을 바로 붙여줘.

  9. ⑨ 안전하게 만들려면 무엇을 지켜야 할지 보기 · 보안·개인정보

    이 서비스를 안전하게 만들려면 무엇을 조심해야 하는지 알려줘.
비밀 열쇠(API 키), 로그인·권한, 개인정보가 이 서비스에서는 어디에 해당할지 예를 들어 설명해줘.
화면만으로 알 수 없는 건 '추측'이라고 표시해줘.

  10. ⑩ 기획 문서로 정리해 보기 · PRD·와이어프레임

    이 서비스를 처음 만든다고 생각하고, 만들기 전에 어떤 기획 문서를 준비했을지 알려줘.
PRD, MVP, 페르소나, 와이어프레임, 기능 명세서, 완료 조건이 각각 무엇인지 쉬운 말로 설명하고, 이 서비스 기준으로 한 줄씩 예시를 써줘.

  11. ⑪ 디자인 규칙과 움직임 보기 · 디자인 시스템·모션

    이 화면에 쓰인 색, 글자 크기, 여백, 버튼·카드 모양에 어떤 규칙이 있는지 찾아서 표로 정리해줘.
버튼을 누르거나 화면이 바뀔 때 보이는 움직임(모션)도 알려주고, 이런 규칙 모음을 뭐라고 부르는지 설명해줘. 확인할 수 없는 건 '추측'이라고 표시해줘.

  12. ⑫ 화면 부품 이름 알기 · 탭·모달·드롭다운 등 UI 부품

    이 화면에 보이는 작은 부품들(예: 버튼, 탭, 드롭다운, 모달, 토글, 카드, 검색창, 배지)을 모두 찾아서 이름을 알려줘.
나는 이런 부품 이름을 하나도 모른다고 생각하고, 각 부품이 화면의 어디에 있고 무슨 일을 하는지 쉬운 말로 설명해줘.
표(부품 이름 | 화면의 어디 | 하는 일 | AI에게 요청할 때 쓰는 말 예시)로 정리해줘.
실습

뜯어본 서비스로 비슷한 서비스 만들기

화면은 복제하지 않고 사용자와 문제 해결 흐름만 참고해 작은 서비스를 만듦.

3.1 만드는 순서

  1. ① 분석 결과 고르기분석 결과 중 내 서비스에 필요한 것만 고름.
  2. ② 내 과제로 바꾸기누가, 어떤 불편을, 무엇으로 해결할지 정함.
  3. ③ 핵심 화면 구현핵심 행동 하나가 되는 첫 화면을 Codex로 만듦.
  4. ④ 직접 눌러 확인직접 눌러 보고 어색한 점을 고쳐 달라고 요청함.

3.2 첫 결과물 만들기 프롬프트

앞에서 정리한 서비스 분석 내용을 참고해, 비슷한 문제를 해결하는 나만의 웹앱 첫 화면을 만들어줘.
참고 서비스의 이름·문구·브랜드 디자인을 그대로 복제하지 말고, 사용자에게 필요한 기능과 이용 흐름만 참고해줘.

[내가 만들 서비스]
서비스 이름: {서비스 이름}
사용자: {누가 사용하는지}
해결할 불편: {어떤 문제를 줄일지}
사용자가 끝내려는 일: {핵심 행동 하나}

[분석 결과에서 가져올 내용]
화면 구성: {필요한 화면 요소}
사용자 흐름: {화면 → 화면 순서}
필요한 정보: {화면에 표시할 항목}

[만들기 조건]
- 초보자가 바로 확인할 수 있는 웹 화면으로 구현해줘.
- 우선 핵심 행동 하나가 작동하는 첫 결과물에 집중해줘.
- 실제 개인정보 대신 가상의 예시 데이터를 사용해줘.
- 로그인, 실제 데이터 저장, 외부 API 연결은 하지 말고 화면 안의 예시 데이터로 동작하게 해줘.
- 주요 버튼과 입력 기능을 직접 눌러 확인하고, 작동하지 않거나 어색한 부분을 수정해줘.
- 실행 방법과 구현한 기능을 마지막에 짧게 알려줘.

첫 결과물은 핵심 기능을 확인하는 시제품으로, 직접 눌러 보고 고칠 점을 요청함.
